# 実機読み取り専用受入れ・データ保護要件

## 1. 優先関係と対象

2026-09-28以降の最終受入れは仮想環境を構築せず、Windows実機で行う。本文書は `21`～`36` のうちHyper-V、VirtualBox、guest、snapshot、VM内TestLabを前提にした実行方法を置き換える。製品の記録品質、必須ケース数、MFT件数、性能閾値、Windows 10実機互換性、ログ保持、履歴復旧は緩和しない。旧仮想環境要件は履歴として残し、実行指示には使わない。

本要件は実機へのあらゆる書込みを一律に禁じるものではない。最優先の禁止事項は、既存ユーザーデータ・システムデータ・外付け媒体に対する編集・削除・移動・名前変更・上書き・切詰め、初期化・フォーマット・パーティション変更、ACL/属性/時刻の変更、共有・サービス・レジストリ設定の変更など、喪失・破損・復旧困難を招く操作である。復旧を試みて元に戻す予定であっても、これらの対象への変更を許可しない。既存のStorage Chronicle履歴・インストールも受入れテストやinstaller試験のために変更・削除しない。Storage Chronicle自身の既存設定ファイルは例外として、ユーザーが通常の製品機能を操作した場合に限り、承認済み製品領域内で更新してよい。設定更新は原子的置換と有効な直前世代の保持を行い、破損時に復旧できること。製品はユーザー/OSの共有・サービス・レジストリ設定を通常設定更新の対象にしない。

「読み取り専用」は、Storage ChronicleのUI、Agent、Session Agent、Collectorが監視対象の既存ユーザーファイル、ディレクトリ、ボリューム、共有設定を変更しないことを指す。製品自身の設定、正本履歴、索引、診断成果物は承認済みの製品専用保存先へ書き込んでよい。ユーザーが有効化した外付け媒体への履歴ミラーも、実ボリュームidentityと製品専用領域を確認した後の追記だけ許可する。既存の媒体データと未知の同名ファイルは変更しない。テスト用workloadは製品と別プロセスとして、当該runで新規作成した専用fixtureの内部だけを変更できる。既存ファイルをfixtureとして流用しない。テスト生成物の削除は、当該runの所有marker、run GUID、許可されたrootとの包含関係、削除対象の個別パスをすべて検証できる場合に限る。どれか一つでも不明なら削除せず、証拠とfixtureを保持して停止する。

「実機データを破壊しない」は既存のユーザーデータ、システムデータ、既存のStorage Chronicle履歴・設定・インストール、既存の外付け媒体を上書き、削除、初期化、フォーマット、権限変更、移動しないことを意味する。ソフトウェア監査だけで無条件の無事故を証明できたとは報告しない。証拠が不足する場合は `NOT_EXECUTED` として停止する。

## 2. 実機起動前の必須監査

トップCodexは製品プロセス、MSI、サービス、特権スクリプト、workloadのいずれも実機で起動する前に、次を現在のコミットに対して実施し、ファイルと行を示した監査結果を `docs/release/physical-readonly-audit.md` に記録する。

1. `src`、`tools`、`build`、`tests`、インストーラー定義、呼び出す外部コマンドの書込み経路を静的に列挙する。P/Invoke、`CreateFile` のアクセスマスク、`FileStream`、`Directory`、PowerShell Storage/DiskPart/SMB/Service操作、IPC経由の間接変更も追う。単なる禁止語検索で完了としない。
2. 製品の既存ユーザーデータに対するhandleとOS APIが読取りまたは通知取得に限定されることを確認する。`GENERIC_WRITE`、`DELETE`、ACL/属性/時刻変更、USN journalの作成・削除・拡張、format、partition、raw physical disk書込み、共有設定変更の経路があれば、実機起動前に隔離・修正・再監査する。製品専用履歴・設定・索引への書込みは別途所有境界を検証する。`SeBackupPrivilege` はメタデータ読取りの限定scopeだけにする。
3. 製品自身の書込み先とテストworkloadの書込み先を絶対パスで列挙し、監視対象の既存ユーザーデータから分離する。媒体ミラーでは専用ディレクトリ、既存セグメント不変、所有manifest、atomic確定を確認する。パス正規化、junction・symlink・reparse point、UNC、Volume GUID、drive-letter変更、既存ファイルの存在を確認する。接続volumeのsystem、boot、recovery、EFI役割は権威ある情報源で分類し、分類不能または書込み時の実ボリューム同一性を確証できない場合は、ミラー登録、履歴復旧、importを含む全媒体書込みを拒否する。マウントポイント文字列の一致だけでは実体同一性の証明としない。
4. unit、contract、architecture、headless、integration、破損・失敗・キャンセル・復旧テスト、DocMirror、警告ゼロbuildを実行する。ただし実機への副作用があるテストはこの段階では起動しない。
5. 読取り専用のhost preflightでOS/build、権限、対象volumeの識別、空き容量、既存製品インストール、既存履歴、保存先、対象媒体、サービス名・共有名の衝突を調べる。検出できない値を安全と推定しない。
6. 意図しない変更を検出する独立した実行時監査方法を定義する。製品の自己申告だけでなく、既存ユーザーデータの事前・事後メタデータ比較とプロセス別書込み監視を組み合わせ、許可した履歴・設定・索引への書込みと区別する。他プロセスの変更と区別できない場合は受入れを保留する。静的監査と実行時監査の両方がPASSするまで通常の監視対象に接続しない。

監査対象コミットが変わった場合、影響範囲を再監査する。監査結果は `PASS`、`FAIL`、`NOT_EXECUTED` と根拠を機械可読成果物にも残す。危険経路が一つでも未解決なら製品を起動しない。

## 3. 変更を許す隔離領域

実I/Oを要するテストは、ユーザーが場所を確認したローカルNTFSの専用ルートに、このrunで新規作成したfixtureだけを使う。リポジトリ、OneDrive、Documents、既存履歴、既存の外付け媒体、ユーザーの通常作業フォルダーをfixture rootにしない。システム・ブート・回復・EFIの既存volumeそのものをformatや大量mutationの対象にしない。VHDXファイルの保存先がC:上の専用ディレクトリであっても、mount後の仮想volumeと物理C:を別identityで検証する。テスト開始前にルートと子孫の実体を解決し、既存データ、reparse point、mount point、別volumeへの逸脱があれば拒否する。新規file-backed VHDXを作成する前の空き容量は40 GiB以上、1M MFT seed作成前は60 GiB以上を必須とし、不足時は件数を減らさず停止する。

VHDXが必要なcapabilityは、承認済みルート内へ新しいファイル名・run GUIDで作るfile-backed dynamic VHDXだけを使う。作成前に同名ファイル不存在を確認し、mount後はファイルパス、disk identity、bus type、partition、volume label、二重marker、run GUIDを独立に照合する。対象diskがphysical、system、boot、pagefile、crashdump、既存データを持つ、または識別に失敗した場合はformat・initialize・deleteを拒否する。DiskPartやStorage cmdletへdisk番号だけを渡して既存diskを操作しない。VHDX内でも既存の内容は上書きしない。

テストで生成したfixtureの後片付けはrun GUIDと所有markerが一致する個別パスに限る。失敗時の証拠と履歴は回収・保持し、対象が曖昧なら削除せず停止する。実機上の既存データを「復旧可能」と見込んで変更してはならない。

## 4. 実機での段階的実行

1. 静的監査と全非特権テストを完了する。
2. 承認済みfixtureと製品保存先だけを使う小規模smokeを行い、独立監査で製品の監視対象書込みゼロを確認する。
3. 同じ境界でUSN/MFT/ETW/通知、再調整、外付け媒体相当、相関、サービス、性能の順に実行する。各段階の証拠がPASSするまで次へ進まない。
4. 既存ユーザーデータを含むボリュームを直接監視する実測は、製品読取り専用経路と独立監査が合格した後に限る。そこでworkloadを実行しない。媒体ミラーの書込み検証は専用VHDXまたはユーザーが選んだ専用テスト媒体で先に行い、既存媒体上では専用領域の所有を確認できる場合だけ有効化する。
5. インストーラーのinstall/repair/update/rollback/uninstallは、既存Storage Chronicleインストールと履歴がないことを確認した専用の物理テストPCだけで実行する。既存PCの製品状態をテストのために変更しない。

Windows 10 22H2の完了には別途その物理環境の実測が必要である。用意できなければ未実行として残す。`NOT_EXECUTED`、fake event、監査不能、データ境界不明をPASSに昇格しない。

## 5. Codexが自律して行える作業

通常ユーザー権限で、要件・コード・スクリプト・MSI定義の調査、書込み経路一覧化、静的解析、非特権・副作用を隔離した自動テスト、監査用ガードの実装、fixture生成スクリプトの準備、manifestと文書の同期、ブランチ統合前レビューを行える。承認済み隔離ルートが確定した後は、その内部の新規fixture作成と検査済みテストを実行できる。権限昇格を自動試行しない。

既存のVirtualBox制御スクリプト、guest専用runner、旧preflightは実機受入れには呼び出さない。トップCodexは既存runnerと文書を実機向けに改修し、旧VM依存の呼び出しを機械確認する。実機での製品起動、監視対象接続、VHDX作成・attach、service操作、MSI実行などは第2節の監査と第3節の境界確認を先に満たす。権限が足りない場合は失敗を記録して人間引継ぎへ進み、Codex本体の管理者起動を要求しない。

## 6. ユーザー操作が必要な境界

ユーザーには次だけを具体的に依頼する。

- 隔離ルートの場所と対象物理PCの確認。既存製品や履歴があるPCではインストーラーマトリクス用の別の物理テストPCを用意する。
- WindowsのUACが表示される製品MSI、サービスまたはfile-backed VHDX操作について、監査済みの具体的な実行内容を確認して承認する。Codexを管理者として再起動しない。
- Explorerの実操作が安定して自動化できない場合に限り、専用fixture内で指定した操作を行う。
- Windows 10 22H2物理テストPCで、監査済みbundleを実行して結果を返す。リモート操作をCodexが勝手に開始しない。
- GitHubの既定ブランチ変更など、Codexに認証・権限がない外部操作を行う。

人間引継ぎには `Blocked`、`Reason`、`WhyUserActionIsRequired`、`DoThis`、`ExpectedResult`、`DoNotDo`、`ResumeCommand`、`SendBack` を含める。ユーザーにはパスワード、プロダクトキー、秘密情報を送らせない。ユーザー操作が完了するまで依存する実機変更処理を開始しない。

## 7. 完了条件

全必須ケースについて実機証拠、製品専用領域以外の監視対象への製品書込みゼロ、隔離領域外のテスト変更ゼロ、既存データの破壊ゼロ、履歴保持、性能・記録品質の合格が揃うこと。静的監査と独立した実行時監査の結果、対象コミット、OS、volume identity、run GUID、対象・保存先、未実行項目を `docs/release/main-readiness.md` に記録する。検証不能または未実行のゲートがあれば `main` へ昇格しない。

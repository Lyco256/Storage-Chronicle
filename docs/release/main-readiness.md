## Current physical-safety gate (2026-09-28)

The user-approved policy prioritizes preventing edits, deletion, overwrite, movement, formatting, initialization, ACL changes, and other data-loss or hard-to-reverse operations on existing real-machine data. Writes to Storage Chronicle's own approved history/settings/index/evidence areas are allowed; external-media mirroring is allowed only in an explicitly enabled, product-owned directory. The physical source audit is currently blocked: see [`physical-readonly-audit.md`](physical-readonly-audit.md) and its machine-readable companion. Product and privileged acceptance runners have not been launched under this policy. Previously identified runner/installer hazards have source-level remediations, but residual installer/cleanup boundaries are `PARTIAL` and all unaudited runtime gates are `NOT_EXECUTED`. Do not connect normal monitored volumes or run physical acceptance, and do not promote to `main`, until the findings are remediated and both static and independent runtime audits pass.

The current integrated source removes the caller-settable `IsVolumeIdentityBound` boolean and path-based media I/O. External-media collection, mirror, import, and recovery require an `IVolumeBoundMediaFileSystem` session; the Windows implementation pins the expected volume, confines production paths to `.StorageChronicle`, uses create-only file creation, and only publishes session-issued streams without replacing destinations. Existing unmarked product roots, unknown root/writer content, and reparse entries are refused. A plain JSON ownership marker is still forgeable, and protection against ancestor `DELETE_CHILD` operations is unproven. The approved policy allows Storage Chronicle-owned history and settings writes through product-owned safe paths, while prohibiting destructive or hard-to-reverse changes to existing user/system data, histories, installations, and media. Existing product settings can be updated through the supported UI/API; settings affecting monitored paths, media mirrors, or Agent behavior must be described to the user before application.

A prior audit found that recovery could rename an unproven pre-existing writer `.tmp`, while the import ledger accepted an arbitrary root and replaced an existing JSON file. The 2026-09-30 external-media integration closes those specific code paths: recovery now requires durable PC-local creation intent bound to content identity, while ledger storage is fixed-root and append-only; adversarial tests verify preservation. This does not prove all media containment: plain JSON media-root ownership remains forgeable, and ancestor `DELETE_CHILD`/reparse race resistance, access-control behavior, and commit-bound physical audit remain incomplete. Do not enable production media writes or run physical acceptance until those remaining gates pass.

The follow-up findings above are superseded only for temporary-segment recovery and PC import-ledger persistence. The media root marker itself is still a plain JSON file and does not establish authorization by itself; explicit mirror settings, protected-role classification, identity binding, pinned-volume I/O, and remaining physical-safety gates still govern whether any media write may occur.

The 2026-09-29 continuation retired the old VM/guest acceptance launch path: `Invoke-WindowsTestLab.ps1` now exits before importing helpers or touching VirtualBox, and Agent `--testlab` exits before host construction, settings reads, or collector startup. The final aggregator no longer accepts TestLab/VirtualBox evidence and now requires a passing physical-safety audit bound to the exact current commit, including static review, host preflight, and independent write monitoring. This is containment and gate hardening, not an acceptance pass: the Windows 10 Stage A composer and several evidence producers still emit/require VM-shaped data, the physical-only runner is incomplete, and the audit JSON remains `NOT_EXECUTED`/stale for the current changes. No physical or VM runner was invoked.

The integrated UI adds separately paged Live/Replay Activity Frame summaries and metadata-only timelines, visible process/location panes, ordering and pinning controls, and configured timeout expiry. Matched ETW ProcessStop is now durable as a separate non-file lifecycle fact (never a synthetic canonical file event), so historical Replay can restore the observed boundary after Agent restart. Default `./build/Test-All.ps1` passed on the current working tree; physical ETW acceptance and stress/performance evidence for long histories remain outstanding, so this does not change the overall **NOT READY** decision.

The current `./build/Test-All.ps1` run on 2026-09-29 reported coverage gates Domain 80.81%, State 94.13%, Projection 89.28%, Storage 85.61%; measured UI ViewModels exceeded 70%.

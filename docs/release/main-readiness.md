## Current physical-safety gate (2026-09-28)

The user-approved policy prioritizes preventing edits, deletion, overwrite, movement, formatting, initialization, ACL changes, and other data-loss or hard-to-reverse operations on existing real-machine data. Writes to Storage Chronicle's own approved history/settings/index/evidence areas are allowed; external-media mirroring is allowed only in an explicitly enabled, product-owned directory. The physical source audit is currently blocked: see [`physical-readonly-audit.md`](physical-readonly-audit.md) and its machine-readable companion. Product and privileged acceptance runners have not been launched under this policy. Previously identified runner/installer hazards have source-level remediations, but residual installer/cleanup boundaries are `PARTIAL` and all unaudited runtime gates are `NOT_EXECUTED`. Do not connect normal monitored volumes or run physical acceptance, and do not promote to `main`, until the findings are remediated and both static and independent runtime audits pass.

The current integrated source removes the caller-settable `IsVolumeIdentityBound` boolean and path-based media I/O. External-media collection, mirror, import, and recovery require an `IVolumeBoundMediaFileSystem` session; the Windows implementation pins the expected volume, confines production paths to `.StorageChronicle`, uses create-only file creation, and only publishes session-issued streams without replacing destinations. Existing unmarked product roots, unknown root/writer content, and reparse entries are refused. A plain JSON ownership marker is still forgeable; local NTFS fixture coverage verifies a pinned product root cannot be renamed or deleted during the session, but behavior across supported removable-media filesystems and independent hostile-writer races is not established. The approved policy allows Storage Chronicle-owned history and settings writes through product-owned safe paths, while prohibiting destructive or hard-to-reverse changes to existing user/system data, histories, installations, and media. Existing product settings can be updated through the supported UI/API; settings affecting monitored paths, media mirrors, or Agent behavior must be described to the user before application.

A prior audit found that recovery could rename an unproven pre-existing writer `.tmp`, while the import ledger accepted an arbitrary root and replaced an existing JSON file. The 2026-09-30 external-media integration closes those specific code paths: recovery now requires durable PC-local creation intent bound to content identity, while ledger storage is fixed-root and append-only; adversarial tests verify preservation. This does not prove all media containment: plain JSON media-root ownership remains forgeable, and ancestor `DELETE_CHILD`/reparse race resistance, access-control behavior, and commit-bound physical audit remain incomplete. Do not enable production media writes or run physical acceptance until those remaining gates pass.

# Performance baseline

The repository contains an opt-in BenchmarkDotNet harness at `benchmarks/StorageChronicle.Benchmarks` and deterministic load generation at `tools/StorageChronicle.TestDataGenerator`. CI records benchmark output under `artifacts/` only; generated output is not committed.

The 50 MiB private-working-set and 0.5% average CPU thresholds are acceptance gates for a release hardware run, not values inferred from a developer workstation. A release is not performance-approved until the run records private working set, CPU average, queue depth, disk writes, and the exact OS/build/configuration.

The latest previous deterministic Event Stack benchmark on this Windows 11 25H2 / .NET 10.0.10 / SDK 10.0.302 / Intel i5-1235U host measured `EventStackPage100K` at 4.523 ms mean (99.9% CI 4.381–4.664 ms) with 3.44 MiB managed allocation. This is a pre-current-worktree baseline, not final post-integration evidence. A fresh release run must include Event Stack, Grouped, Period Diff, one-million-node path reconstruction, large-folder move, append/Zstandard/SQLite, media manifest, and—on a configured Windows host—the MFT capability benchmark. Benchmark artifacts are generated under `artifacts/benchmarks` and are intentionally not committed.

The product-level idle gate is measured with `build/quality/Test-ResourceBudget.ps1 -ProcessId <agentPid>,<sessionAgentPid> -DurationSeconds 600`. The monitor records `PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize`, working set samples, normalized CPU, and Windows process-I/O write bytes. Queue depth is exposed by the Agent health IPC contract and must be checked alongside the JSON result. The accepted run must cover startup through ten minutes with no bulk events during the final five minutes.

## R-03/R-19 acceptance audit (2026-08-03)

The focused `build/quality/Test-Performance.ps1` has a default filter of `*StorageChronicleBenchmarks*`, so it does not select the separate `LargeFolderMoveBenchmarks`, `StorageAppendBenchmarks`, `SqliteRebuildBenchmarks`, `MediaManifestBenchmarks`, `MediaSegmentAppendBenchmarks`, or `WindowsMftBenchmarks` types. The existing benchmark artifacts inspected during this audit contained only an `EventStackPage100K` result. This is not full-matrix evidence.

The supplemental `build/quality/Test-FullBenchmarkMatrix.ps1` runs each required suite separately, validates every expected method in full-compressed JSON, and writes a manifest under `artifacts/benchmarks/full-matrix-*`. A release acceptance run must use `-IncludeMft` with a dedicated `STORAGE_CHRONICLE_MFT_VOLUME`; `-PortableOnly` records `AcceptanceEligible=false`. Benchmark declarations were corrected so BenchmarkDotNet can execute real modules, and each benchmark type explicitly uses one measured iteration with no warmup; this is a deterministic workload measurement, not a statistical stability claim. The bounded canonical batch writer and 512-record SQLite recovery batches keep the real workload executable without dropping events or weakening `synchronous=FULL` durability.

The current bounded-batch portable matrix completed on 2026-08-03 under `artifacts/benchmarks/portable-matrix-current/full-matrix-20260803T122827484Z`. Its manifest reports `ExecutionStatus=completed`, six passed non-MFT suites, and all 12 expected methods. The measured means were: Event Stack 744.730 ms, Grouped 3,729.204 ms, Period Diff 516.007 ms, one-million-node path reconstruction 2,179.920 ms, large-folder move 0.409 ms, append plus SQLite index 6,878.722 ms, compressed segment close 8,758.877 ms, SQLite rebuild 5,817.080 ms, indexed count 12.268 ms, media manifest import 2,287.801 ms, media manifest validation 1.744 ms, and media segment append 2,733.527 ms. This is current-code diagnostic evidence, not release acceptance: `PortableOnly=true`, `IncludeMft=false`, and `AcceptanceEligible=false`; the configured MFT suite and the 600-second resource gate remain pending.

The existing resource script validates target PIDs only before starting, accepts caller-supplied relaxed threshold parameters, and does not itself validate that the monitor's sample timestamps span the requested duration or that the supplied PIDs retain the same process identity throughout. `build/quality/Test-ResourceBudgetAcceptance.ps1` supplements it without replacing it: it fixes the R-03 thresholds at 50 MiB/0.5%, supervises both Agent and Session Agent, preserves process lifecycle and child-output evidence, validates the result interval and counters, and requires external JSON quiet-period evidence (`QuietPeriodSeconds >= 300`, `BulkEventCount = 0`) whose timestamp interval is inside the measurement and reaches its end. The resource IPC client was corrected to use cancellable asynchronous named-pipe I/O. A current 15-second diagnostic with the actual Release Agent and Session Agent under `artifacts/quality/resources/acceptance-2536-40368-20260803T132222166Z.json` produced complete queue sampling with zero missed samples and stayed below the diagnostic CPU/private-memory thresholds; it is not acceptance evidence because it is diagnostic and shorter than 600 seconds.

A deliberate one-second diagnostic with a temporary process and no Agent health pipe failed closed and emitted `AcceptanceEligible=false`; this validates the failure path only and is not a product or release measurement.

Previous pre-current-worktree acceptance run on 2026-08-02: Agent PID 41464 plus Session Agent PID 456, 583 samples over 600 seconds, peak combined private working set 14.53125 MiB, peak combined working set 80.7890625 MiB, average normalized CPU 0.0110659393%, and process-I/O writes 989,120 bytes. Both enforced thresholds were false (`PrivateMemoryLimitExceeded=false`, `CpuLimitExceeded=false`). The test configuration used an empty temporary monitoring root to ensure the final five minutes contained no bulk events; the temporary configuration was removed after the run. This is historical baseline evidence, not current post-integration acceptance.

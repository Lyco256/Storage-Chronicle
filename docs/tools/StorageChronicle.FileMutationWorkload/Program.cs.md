# Program.cs

This console workload performs real file-system mutations inside a disposable, marker-identified TestLab data volume. It supports basic create/write, a full metadata lifecycle, zero-delay burst, two-child-process parallel workload, directory move, directory delete, short-lived files, an ACL-denied metadata-only candidate, and MFT-scale zero-byte create scenarios. The full and MFT scenarios distribute entries through nested directories; the parallel scenario records each child process's operation oracle. Each operation record includes UTC start and completion fields. The ACL-denied scenario applies a deny rule for the current identity to the candidate file and is permitted only on a disposable TestLab volume; the workload never reads or hashes file contents.

The oracle uses schema `StorageChronicle.FileMutationWorkload.v2` and includes the primary process plus a `Processes` collection containing each child process ID, start time, executable path, and scenario ID, along with operation, relative paths, and sequence. The parent merges child process evidence only from completed child oracle documents and prefixes the worker directory to each child operation path; missing/partial child evidence remains an acceptance failure rather than being synthesized. `run-id` must be a GUID and the oracle must be the non-existing direct child `oracle-<run-id>.json` of the verified root (workers use a run-specific worker suffix). Before reading markers or mutating data, the workload rejects roots under Windows, Program Files, ProgramData, any current user profile/Documents path, configured OneDrive roots, and a repository discovered from its working directory or executable path. The root must already exist, must not be a volume root or the guest system volume `C:`, and must be on a marked TestLab volume. Both marker JSON files with schema `StorageChronicle.TestLabDataMarker.v1`, the requested run ID, approved role, label, filesystem, and a non-empty `VolumeUniqueId` are required before mutation; the workload resolves the live volume GUID with `GetVolumeNameForVolumeMountPoint` and requires both markers to match. The workload never creates a marker on an unmarked path. It refuses any reparse point or root entry other than those two marker files. Every initial data/oracle file is opened with `FileMode.CreateNew`; existing oracle paths are refused, and no outside-root oracle path is accepted. Before recursive directory-delete scenarios, the observed tree must exactly match the names generated by this run, and unexpected/reparse entries stop deletion. Failure leaves the partially populated fixture in place and produces no final oracle, so it must not be reused; preserve it for evidence and investigate. The policy guard is covered by Architecture tests for profile, OneDrive, repository, and near-prefix paths. The marker remains caller-provided JSON, and workload I/O still uses path-based calls after preflight; concurrent replacement and marker authenticity are not certified. Directory moves/deletes are recorded as one parent operation, leaving descendant reconstruction to Storage Chronicle.
